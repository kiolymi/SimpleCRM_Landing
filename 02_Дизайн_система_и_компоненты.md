# Этап 2 из 5 — Foundations, дизайн-система и библиотека компонентов

## Роль и цель

Ты продолжаешь работу в том же Figma-файле после этапа 1. Создай production-ready foundations и библиотеку компонентов универсальной русскоязычной CRM для iPhone и iPad. Цель — абсолютная консистентность и адаптивность: разработчик должен видеть не россыпь ручных копий, а понятную дизайн-систему и переиспользуемые компоненты.

Итог проекта: редактируемые, аккуратные, русифицированные экраны всех документированных сценариев; точное сохранение внешнего вида и UX эталона; готовность для разработки и лендинговых mockup.

## Обязательные правила

- Не меняй и не удаляй исходные скриншоты и карту покрытия этапа 1.
- Не создавай новый Figma-файл. Работай только в `02 — Foundations` и `03 — Components` текущего canvas.
- Повторяющиеся значения должны стать Figma Variables/Styles; повторяющиеся UI-паттерны — компонентами. Не оставляй ручные клоны на будущих экранах.
- Сначала извлеки значения из референсов; не подменяй эталон случайным «красивым» стилем.
- Текст должен быть живым русским текстом. Все текстовые компоненты обязаны нормально переживать более длинные строки: Auto Layout, HUG/FILL, min/max размеры, корректный перенос; не микроскопический шрифт и не обрезка.
- Воспроизводи только видимые системные iOS-элементы; не добавляй декоративный iPhone UI, которого нет в эталонном сценарии.
- Используй вымышленные русские данные и сохранённый словарь этапа 1.
- После завершения этого этапа остановись. Не собирай полноэкранные продуктовые потоки до промпта этапа 3.

## 1. Foundations — извлечь, а не угадать

В `02 — Foundations` создай наглядные, подписанные и редактируемые блоки:

### Цвета и семантика

Извлеки из скриншотов и зафиксируй базовые и семантические значения:

- app/page background;
- surface/card/modal;
- primary, secondary и muted text;
- primary/accent action;
- border/divider;
- selected/active/pressed;
- success, warning, error, info;
- disabled text/fill;
- overlay/scrim;
- event/status colors календаря.

Создай Variables с осмысленными именами, например `color/text/primary`, а не случайными названиями. Если в эталоне нет dark mode, не выдумывай его.

### Типографика

Определи по референсам:

- font family и доступные начертания;
- display/large title/title/section title/body/body small/caption/button/label;
- font size, weight, line-height, letter spacing;
- цвет и правила переноса.

Создай Text Styles. Для каждого стиля покажи образец на русском с длинным текстом. Отдельно проверь длинный заголовок, название клиента, filename, многострочное описание и error message.

### Layout, spacing и surface

Зафиксируй:

- базовую единицу отступов и её шкалу;
- экранные горизонтальные отступы;
- вертикальные ритмы;
- высоты строк и touch targets;
- радиусы;
- border widths;
- тени;
- размеры иконок;
- высоту navigation/tab bar;
- safe-area правила;
- ширины iPhone/iPad, определённые на этапе 1.

Покажи все значения на редактируемых визуальных образцах. Если одно значение встречается много раз, сделай его переменной.

## 2. Системные каркасы

Создай компоненты/заготовки каркаса, необходимые для дальнейших экранов:

- `Shell / iPhone / Base` с корректными зонами status bar, navigation, scroll area, fixed bottom area и home indicator;
- `Shell / iPhone / Keyboard open`;
- `Shell / iPad / Expanded sidebar`;
- `Shell / iPad / Collapsed sidebar`;
- `iOS / Navigation bar` (back, title, right action и варианты);
- `iOS / Tab bar` или иной нижний nav-паттерн, если он подтверждён референсом;
- `iOS / Action sheet`, `iOS / Alert`, `iOS / Bottom sheet`, `iOS / Toast`, `iOS / Permission` — только в тех конфигурациях, которые есть в источниках.

Не имитируй «телефон в рамке» внутри рабочих экранов: shell должен быть удобной инженерной основой. Device mockup будет создан отдельно на этапе 5.

## 3. Библиотека компонентов

В `03 — Components` собери компоненты с Auto Layout и логичными variant properties. Каждая карточка/компонент должна содержать название, назначение и видимые варианты. Сначала сопоставь их с референсом, затем создавай.

Обязательный охват:

### Базовые действия и ввод

- Primary, secondary, tertiary/text, destructive и icon buttons;
- back/close/add/more actions;
- input, textarea, search, date/time field, select/dropdown, picker;
- checkbox, radio, switch;
- field label, hint, required, validation error;
- segmented control и tabs.

Варианты там, где релевантно: `default`, `pressed`, `focused`, `filled`, `empty`, `disabled`, `loading`, `error`, `selected`.

### Контент и навигация

- sidebar item и sidebar profile;
- bottom navigation item;
- list row, setting row, disclosure row;
- avatar и client identity row;
- status/chip/badge;
- appointment/event card;
- calendar cell и time-slot;
- client card;
- task row;
- notification row;
- file row;
- note/document row;
- message list row и message bubble;
- empty state, loading/skeleton, inline error, network error;
- modal, confirmation dialog, bottom sheet, dropdown/menu, toast.

### Состояния

Везде, где этого требует референс или стандартное поведение, включи: selected/unselected, unread/read, completed/open, expanded/collapsed, with/without avatar/icon, one/two/multi-line title, long Russian text, destructive/confirmation, disabled/loading/error.

## 4. Точные правила конструкций

- Родительские контейнеры со структурными детьми — Auto Layout. Внутренние отступы, gaps и alignment должны быть заданы на контейнере.
- Текст: явная ширина там, где он должен переноситься; `HUG` там, где должен расти; не делай контент разрушаемым при длинном русском тексте.
- Иконка + текст: иконка не должна сжиматься/съезжать; текст должен получать доступное пространство.
- Кнопки: не обрезать русские глаголы; увеличивать ширину или использовать корректный layout.
- Длинные имена и файлы: применить подтверждённое эталоном поведение (перенос или ellipsis), а не произвольное.
- Компоненты должны иметь осмысленные имена вида `Button / Primary / Enabled`, `Field / Text / Error`, `Row / Client / With status`.
- Добавь короткое description к каждому компоненту: назначение, допустимые состояния и где использовать.

## 5. Проверочный набор русских строк

Собери `Localization stress test` — небольшой frame с экземплярами основных компонентов и строками, которые обычно ломают вёрстку:

- «Запланировать новую консультацию»;
- «Защищённые сообщения»;
- «Александра Константиновна Воронцова»;
- «Не удалось сохранить изменения. Проверьте подключение к интернету и повторите попытку.»;
- «Файл с результатами первичной консультации.pdf»;
- «Уведомления о начале встречи».

Исправь компоненты так, чтобы все строки выглядели профессионально, не пересекались и не обрезались.

## Контроль качества

До отчёта проверь:

- foundations соответствуют скриншотам, а не выдуманному стилю;
- все токены и стили имеют понятные названия;
- все компоненты редактируемы, с Auto Layout и вариантами;
- русские stress-тексты не ломают ни один элемент;
- элементы имеют достаточные зоны нажатия;
- нет разрозненных «слегка разных» цветов, радиусов, отступов и шрифтов;
- iPhone/iPad shell и iOS overlays готовы для сборки экранов;
- `Coverage map` обновлена: компоненты/foundations, необходимые для экранов, имеют статус `Done` или явно отмечены `Needs reference`.

## Что вернуть в отчёте и где остановиться

Верни: ссылки/ID созданных foundations, variables/styles, component sets, перечень variants, результаты localization stress test, а также открытые пробелы в референсах. Затем **остановись**. Не строй полноценные Calendar/Clients/другие экраны до следующего промпта.
