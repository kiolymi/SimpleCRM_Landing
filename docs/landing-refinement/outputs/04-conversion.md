## Варианты в зависимости от подтверждённого продукта

| Условия | Основная кнопка | Куда ведёт | Что надо подтвердить |
|---|---|---|---|
| Готовая доступная версия | «Начать работу» либо точная кнопка магазина | Проверенная регистрация/конкретная карточка приложения | Платформы, доступ, отсутствие заглушки, реальные следующие действия |
| Подтверждённый пилот и команда принимает заявки | «Запросить доступ» | Короткая форма именно на доступ | Контакт/endpoint, кто и как отвечает, ограничения пилота, разрешённый тест |
| Есть только согласованный контакт | «Обсудить начало работы» | Явно обозначенный канал команды | Адрес, его назначение и разрешение размещения; без выдуманного SLA |
| Текущая неизвестность | «Посмотреть сценарии» | #practice, три реальные локальные демонстрации | Работоспособность примеров; это не конверсия в приложение |

До ответа Q002/Q004 выбрать четвёртый вариант для локального черновика. Финальный блок «Хотите попробовать в своей практике?» может честно сообщать, что способ получения доступа ещё уточняется, но не изображать запись в лист ожидания. Нельзя объявить goal завершённой на таком варианте. После ответа владельца заменяются label/href и итоговый путь без смены всей композиции.

Соседняя ссылка в промежуточной версии: «Как начать» → #start. Она объясняет последовательность и состояние доступа; не открывает выдуманную регистрацию. В готовом варианте вторичная кнопка «Посмотреть пример» продолжает вести к #practice.

## Спецификация короткого запроса доступа

Проектируется, но не подключается без адресата. На отдельном участке #start или отдельном маршруте, не в технической поддержке.

- Заголовок «Начать работу с Simple CRM»; подзаголовок зависит от подтверждённого режима, без «14 дней»/«бесплатно» по умолчанию.
- Email — обязательный контакт при утверждённой email-доставке; имя необязательно. Короткое поле «Что хотите упростить?» необязательно. Профессия/телефон/размер базы не обязательны без доказанной необходимости.
- Никаких клиентских баз, медицинских заметок, файлов и данных клиентов на первом шаге.
- Отдельное незаполненное согласие/уведомление по утверждённому тексту владельца, ссылка на действующую политику. Этот документ не является юридическим заключением и не изобретает текст обязательств.
- Кнопка «Отправить запрос» только при настроенном реальном канале. Рядом — куда идёт обращение и что будет дальше. Никаких неподтверждённых «ответим за час».

## Состояния и повтор

| Состояние | Что видит человек | Поведение |
|---|---|---|
| idle | Пустые поля и понятная цель | Можно вводить и уходить без отправки |
| invalid | Точное поле: «Укажите email, чтобы команда могла ответить» | Фокус на первом проблемном поле, остальные значения сохранены |
| submitting | «Отправляем…» | Один запрос; кнопка блокирует повторный клик, статус озвучивается |
| accepted | «Запрос принят» + подтверждённое пояснение следующего шага | Только после согласованного ответа backend; не при каждом HTTP 200 и не после валидации |
| delivery-pending | «Запрос сохранён, доставка команде ещё не подтверждена» | Если backend различает приём и доставку, UI не смешивает их |
| failed | «Не удалось отправить. Попробуйте ещё раз» | Поля сохранены; ручной повтор, без бесконечной фоновой отправки |
| timeout / uncertain | «Подтверждение не получено» | Не говорить, что ничего не было отправлено; повтор с тем же ключом/ID если это поддержано договорённым контрактом |
| duplicate | «Этот запрос уже принят» | Дедупликация по договорённому request id, не потеря заявки |
| unconfigured | «Отправка пока не подключена» | Нет сети и ложного success; не собирать контакты в пустоту |

События приёмки и доставки различаются. Не обещать физическое получение email на основе enqueue. Политика хранения, защита от спама и обработка согласий — ответственность утверждённого backend/сервиса, не фронтенд-заглушки.

## Контракт и проверка без реальных отправок

В UI отделить адаптер отправки от формы. Его контракт в плане: sendRequest(payload, requestId) возвращает один из accepted / delivered / failed / uncertain / unconfigured с безопасным сообщением и идентификатором квитанции, если он есть. Конкретный endpoint/провайдер не выбран. Не размещать токены или секреты в репозитории и клиентском JS.

Для локальных тестов внедряется test adapter, явно маркированный как тестовый. Он симулирует accepted, failure, timeout, double-click и invalid; не выполняет fetch и не пишет персональные данные в аналитику/storage. Его результат не попадает в публичную версию как реальная доставка. Без конфигурации production adapter возвращает unconfigured, а UI не показывает рабочую форму отправки.

Критерий CTA_DELIVERY закрывается проверенной действующей ссылкой установки/регистрации либо отдельным разрешённым end-to-end тестом до подтверждения получателя. Если нужен реальный тест письма, предварительно уточнить адрес, данные и разрешение; использовать вымышленные тестовые значения. В этом этапе теста не было.

## Разделение начала и поддержки

Первый пользователь: сценарии → как начать → подтверждённый доступ/контакт. Действующий пользователь: поддержка → тема проблемы/версия по необходимости → обращение. Материалы/FAQ помогают обоим, но не заменяют старт. На pricing до утверждения условий — нейтральная информация о порядке получения доступа, без мнимого покупки тарифа.

Понятность PASS: label соответствует следующему действию. Согласованность PASS: ограничения F12/F13/W03 и возражения аудитории учтены. Сохранность PASS: внешних действий нет. Проверка PASS для спецификации: code + browser baseline; реальная доставка NOT_VERIFIED.
