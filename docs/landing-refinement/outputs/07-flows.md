## 1. Следующий контакт: сначала договорённость, затем решение человека

| Из → в | Инициатор / действие | Данные и результат | Исключение / восстановление |
|---|---|---|---|
| Клиент → новая задача | Специалист «Напомнить мне» | Клиент, краткое действие, дата; задача связана с клиентом | Нет даты: попросить выбрать; пустой текст: «Что нужно сделать?»; значения сохранены |
| Новая задача → сохранено | Специалист подтверждает | Записана задача, а не исходящее сообщение | Ошибка сохранения: остаётся черновик, повтор без дубликата по согласованному backend-контракту |
| Сохранено → «Сегодня» | Наступила выбранная дата | Карточка «Связаться с Еленой», причина и ссылка на историю | Срок прошёл: «Планировали18 сентября», не обвиняющий красный штраф; дата не гарантирует доставку push |
| «Сегодня» → история | Специалист открывает клиента | Видно последнее соглашение и последнюю коммуникацию | История пустая: «Пока нет записанных договорённостей»; не сочинять контекст |
| История → черновик | Специалист выбирает «Подготовить сообщение» | Обычный шаблон с именем; правка текста; источник шаблона ясен | Канал не подключён: объяснить это, не показывать действующую отправку |
| Черновик → отправка | Специалист явно нажимает | Предпросмотр получателя/канала/текста; один запрос | Ошибка: текст сохранён. Неизвестный исход: проверить историю, не слепо дублировать |
| Отправка → отправлено | Подтверждённый статус канала | Время и статус отправки в истории, задача завершена по правилам продукта | «Отправлено» не равно «прочитано» и не означает «клиент записался» |
| Черновик → позже/пропустить | Специалист выбирает другое решение | Перенести свою задачу или завершить без отправки | Клиент отказался от контакта: не создавать новые предложения автоматически |

Никакой автоматической «реактивации» всей базы. Частота и уместность контакта определяются человеком; для психолога не делаем выводы о состоянии клиента и не используем чувствительные записи в шаблоне. AI вне текущей реализации.

В лендинге:3 шага, кнопки симулируют выбор, текст «Ничего не отправлялось». Не предлагать вводить реальный адрес. В приложении необходимы реальные сохранение, канал, дедупликация и статусы — здесь не реализуются.

## 2. Предоплата: две независимые линии состояния

Запись: черновик → ожидает подтверждения/предоплаты → подтверждена → состоялась/отменена. Платёж: не выставлен → ожидается → проверяется → получен частично/полностью либо подтверждённый отказ. Возврат имеет своё ожидание/результат. Эти линии связаны правилами, но одна не подменяет другую.

| Из → в | Инициатор / действие | Данные и результат | Исключение / восстановление |
|---|---|---|---|
| Встреча → счёт | Специалист задаёт стоимость и нужную предоплату | meeting-demo-01;3 000/1 000/2 000; валюта, получатель, срок, версия условий | Предоплата<0 или>стоимости: ошибка поля. Изменение условий после отправки требует новой версии/согласования |
| Счёт → клиентский просмотр | Специалист выбирает разрешённый канал или копирует действительную ссылку | Клиент видит свою услугу, дату, сумму и условия | Нет канала/ссылки: локальный черновик, не «отправлен». Реальный URL/доступ пока Q005 |
| Просмотр → платёж | Клиент проверяет условия и явно подтверждает | Открывается только согласованный платёжный способ; не хранить данные карты на лендинге | Условия не приняты/нет способа: не инициировать платёж |
| Платёж → проверяется | Возврат от провайдера без итогового подтверждения | «Проверяем оплату. Пока не платите повторно» | Нажатие «Я оплатил»/возврат в браузер сами по себе не переводят в received |
| Проверяется → частично получено | Подтверждённое событие провайдера или разрешённое ручное подтверждение специалиста | В истории отдельное основание; received1 000,remaining2 000 | Повторное событие не суммировать повторно. Ручной способ должен обозначаться как ручной |
| Частично → полностью | Подтверждён оставшийся платёж2 000 | received3 000,remaining0 | Частичное списание не считать полной оплатой. Переплата — отдельная проверка, не отрицательный «долг» |
| Платёж → отказ | Провайдер подтвердил отказ | «Оплата не прошла», безопасный повтор | Timeout не отказ; при uncertain сначала сверить результат |
| Встреча → перенос | Стороны согласовали новое время | Связь со счётом сохраняется; дата обновляется; клиент видит новое время | Смена услуги/стоимости: показать перерасчёт и условия, не переносить деньги молча между клиентами |
| Встреча → отменена | Клиент/специалист явно подтверждает отмену | Сообщение об отмене; исходящие напоминания об этой записи прекращаются | Возврат денег — отдельное правило/операция. Не обещать автоматический полный возврат |
| Возврат → ожидание/подтверждён | Разрешённая операция + статус провайдера | Отдельные суммы получено/возвращено, квитанция если есть | Ошибка/неизвестно — не писать «возвращено» |

### Напоминания об оплате

Проектируемая настройка: кому, о какой сумме, когда, через какой доступный канал, шаблон, возможность выключить. Не принимать текущую надпись «Автоматически» в Figma за работающую интеграцию.

Перед каждой отправкой проверять актуальный остаток и состояние встречи, а не только первоначальный таймер. Прекращать при получении нужной суммы, отмене/аннулировании счёта, ручной остановке или отказе клиента от разрешённых сообщений. В uncertain/checking не отправлять требование повторного платежа. При споре/переплате — ручная проверка. Тихие часы и частота — утверждаемые настройки; не выбирать «каждый день» как обязательную норму частной практики.

Лендинг показывает обычный сценарий и переключатель состояния «Ожидание / Предоплата получена / Нужна проверка». Ошибка и отмена доступны в расширенном прототипе Figma. Никаких платёжных реквизитов, подключений и настоящих квитанций.

## 3. Выбор времени по ссылке: клиентская web-страница

| Из → в | Инициатор / действие | Данные и результат | Исключение / восстановление |
|---|---|---|---|
| Настройка → опубликованное расписание | Специалист выбирает услугу, длительность, доступные часы и режим подтверждения | Показываются только свободные часы, без имён других клиентов | Неполные условия/неподключённая оплата: не публиковать неподтверждённый путь |
| Ссылка → выбор | Клиент открывает | Имя специалиста, услуга50мин, цена, часовой пояс, выбор дня/времени | Ссылка недействительна: понятное состояние, без утечки чужих данных |
| Выбор → временное удержание | Клиент нажимает15:00 | Сервер повторно проверяет доступность; ID и срок удержания | Конкурент уже занял: time-unavailable, предложить актуальные варианты, сохранить введённое |
| Удержание → контакт и условия | Клиент вводит минимум | Имя и один утверждённый канал связи; никаких диагнозов/полной базы; условия видны до подтверждения | Ошибка поля у соответствующего поля; неоплаченная форма не отправляется сама |
| Данные → подтверждение без предоплаты | Клиент явно подтверждает, сервер атомарно фиксирует | meeting id, дата/время/tz/длительность, место/онлайнформат | Если специалист подтверждает вручную, итог «Запрос отправлен», не «Запись подтверждена» |
| Данные → предоплата | Если для этой услуги требуется | Переход к правилам сценария2; расписание и платёж связаны одним reservation id | Истёк срок до оплаты: не списывать для потерянного времени; вернуть к доступным часам |
| Предоплата → проверка → подтверждено | Подтверждены и деньги, и резервирование | Клиент получает один непротиворечивый итог | Платёж пришёл после потери времени: состояние «Оплата получена, время не подтверждено», ручное урегулирование/возврат по правилам, не ложный успех |
| Подтверждено → перенос | Клиент открывает разрешённую ссылку управления | Видит свою запись, выбирает новое время; старая сохраняется до успешного атомарного переноса | Новое занято: старая встреча остаётся, клиент выбирает другое |
| Подтверждено → отмена | Клиент видит последствия и подтверждает | Отмена записи отдельно от возврата | До подтверждения не освобождать время; после отмены не предлагать «перенести» уже несуществующую бронь |

Срок удержания: приходит из утверждённого серверного правила, не выдумывается фронтендом. В Figma возможен текст «Время удерживается ещё03:00» только как пример состояния, не продуктовая норма. При истечении сохраняются контакты лишь в пределах утверждённой политики/сессии, не через скрытое постоянное хранилище.

Часовой пояс явно выбран/показан, дата и время однозначны. Для примера15:00Москва =12:00UTC. Услуга50мин не меняется при смене зоны. Если оплата нужна до подтверждения, оба условия показываются заранее. Лендинг не собирает контакт и не запускает реальный countdown, способный выглядеть срочностью продажи.

## Минимальный старт и импорт

Минимальный путь после реального получения доступа: создать одного вымышленного тестового клиента → назначить встречу → записать следующий шаг → посмотреть историю. В рабочем продукте разрешённость обработки реальных данных проверяется отдельно. Не заставлять человека импортировать базу ради первого понимания.

Импорт необязателен и F11 unknown. Проектная последовательность: выбрать поддерживаемый формат (ещё не подтверждён) → сопоставить поля → предпросмотр нескольких строк → отметить дубликаты → показать число создаваемых/пропущенных/ошибочных записей → явно подтвердить → получить отчёт. При ошибке строки не теряются без объяснения; повтор не должен удваивать базу. Не загружать реальные файлы в лендинг и не обещать импорт из любого сервиса.
