# Simple CRM — план сборки маркетингового сайта

**Статус:** Этап 1 из 5 завершён 23 августа 2026. Этот документ — план, а не реализация интерфейса.

## 1. Исходные данные и границы работы

Изучены:

- `гайд для агента — создание лендинга Simple CRM.md` — полный build guide;
- `прототип лендинга Simple CRM.md` — полный аудит структуры и адаптивного поведения референсного сайта;
- `06_STAGE5_REBUILD_PLAN.md` и `stage5-final-state.json` — подтверждённые продуктовые потоки и карта макета;
- макет Simple CRM в Figma: `CHi07sT4Waf6uIkl14hYjN`, обзор canvas доступен в браузере;
- `simple-crm-logo-refined.png` и варианты логотипа.

Маркетинговый сайт повторит полезную информационную архитектуру прототипа: главная → продуктовые возможности → доверие → доказательства → большой сценарий → материалы → следующий шаг; затем — внутренние страницы и единый шаблон статей. Все тексты, изображения, отзывы, цены, юридические сведения, ссылки и продуктовые скриншоты будут создаваться или предоставляться специально для Simple CRM.

Никакие реальные скриншоты продукта не вставляются до отдельного утверждения главной. До этого каждый продуктовый слот отображает единый нейтральный `ProductDeviceMockup`.

## 2. Текущее состояние рабочего проекта

### Стек и точки входа

В текущей рабочей папке нет веб-приложения:

- отсутствуют `package.json`, lockfile, `src/`, `app/`, `pages/`, `components/`, `public/` и конфигурация сборщика;
- отсутствуют команды запуска, production build, lint, typecheck и тесты;
- отсутствуют router, UI-компоненты, design tokens, формы и image pipeline;
- Git-репозиторий не инициализирован, поэтому `git status` неприменим;
- есть только документация, экспортные изображения, JSON-состояния и папка `.audit/` с диагностическим материалом.

Следовательно, на Этапе 1 нельзя безопасно выбирать фреймворк, package manager, структуру маршрутов или создавать дублирующую архитектуру. После получения реального репозитория или отдельного разрешения на создание нового проекта нужно сначала принять его существующую структуру, а не создавать параллельную.

### Доступные брендовые и продуктовые материалы

- В Figma зафиксированы 198 продуктовых экранов, из них 159 iPhone; это подтверждает, что первым источником будущих product shots должны быть подготовленные экраны самого Simple CRM.
- В состоянии макета указано шесть подготовленных landing mockups и шесть отдельных экспортов. Их можно рассмотреть как будущий источник изображений только после утверждения главной и проверки конкретных frame URL/прав на экспорт.
- `simple-crm-logo-refined.png` имеет размер 1254×1254, но это непрозрачный raster (`24bpp RGB`) с запечённой шахматной подложкой. Для header/footer нужен прозрачный исходник: лучше SVG, допустим прозрачный PNG без фона. Сам знак и его синий акцент можно использовать как визуальную основу, но точный брендовый HEX пока **требует подтверждения**.

### Подтверждённые продуктовые факты

Ниже перечислено только то, что отражено в продуктовой карте и макете:

- раздел «Сегодня»: ближайшая встреча, задачи, непрочитанные сообщения, просроченные счета, новые запросы и быстрые действия;
- календарь и поток записи: выбор клиента, дата/время, сохранение, детали, перенос или отмена;
- клиент 360: поиск, обзор, активность, контакты, встречи, задачи, сообщения, документы и счета;
- сообщения: входящие, поиск получателя, диалог, вложение, отправка, success/failed/retry;
- задачи: создание, приоритет, срок, исполнитель, завершение/возврат/удаление;
- документы и платежи/счета;
- глобальный поиск по клиентам, встречам, сообщениям, задачам, документам и счетам.

Не подтверждены и не должны заявляться в copy без данных владельца продукта: лиды, воронки сделок, сегментация, теги, веб-dashboard, аналитика, интеграции, импорт/синхронизация, планы/цены, бесплатный период, SLA, юрисдикция, сертификации, политика обработки данных и любые измеримые результаты.

Этап 1 не создаёт маршруты. Ниже — карта, по которой должна строиться будущая навигация. Ссылки выводятся только после создания соответствующего маршрута; временных `#`-ссылок не будет.

## 5. Карта будущих файлов и компонентов

Текущий стек неизвестен, поэтому эти имена — карта ответственности, а не разрешение создать все папки заранее. После передачи исходного проекта необходимо выбрать **одну** его нативную схему: например, `app/` для app-router, `pages/` для pages-router или аналог выбранного фреймворка. Одновременно создавать все варианты нельзя.

| Назначение | Планируемая единица | Ответственность |
| --- | --- | --- |
| Global styles | `styles/tokens.*` и `styles/global.*` либо существующий token layer | Семантические цвета, типографика, размеры, focus и motion. |
| Site shell | `SiteLayout`, `Container`, `Section` | Общий белый canvas, header/main/footer, ограничения ширины и вертикальный ритм. |
| Навигация | `Header`, `DesktopNav`, `ResourceDropdown`, `AnnouncementBar`, `MobileMenuDialog`, `Footer` | Реальные маршруты, keyboard-safe dropdown и dialog. |
| Базовый UI | `Button`, `TextLink`, `SurfaceCard` | Единые интерактивные состояния и контраст без копирования markup. |
| Изображения продукта | `ProductDeviceMockup` | Один API для placeholder и будущего изображения; сохранение пропорций. |
| Главная | `HeroProduct`, `FeatureProductGrid`, `TrustSplit`, `TestimonialMasonry`, `ProductShowcase`, `ArticleGrid`, `FinalCta` | Семь секций в фиксированной смысловой последовательности. |
| Контент | `content/articles.*`, `ArticleCard`, `ContentHubPage`, `ArticleLayout`, `TableOfContents`, `ArticleSidebar`, `SearchForm` | Данные отдельно от layout; один шаблон для всех статей. |

### Контракт `ProductDeviceMockup`

```ts
type ProductDeviceMockupProps = {
  mode: 'placeholder' | 'image'
  device: 'phone' | 'tablet' | 'desktop'
  label: string
  image?: ImageAsset
  alt?: string
}
```

- `phone`: портретный корпус, соотношение 390:844; нейтральные status bar и 2–4 skeleton-блока.
- `tablet`: широкий корпус в соотношении 4:3; нейтральная сетка без выдуманных данных.
- `desktop`: canvas 16:10 с sidebar и skeleton-панелями.
- В `placeholder` нельзя показывать имена, суммы, аватары, мелкий псевдо-UI или называть экран «реальным скриншотом».
- В `image` меняются только `mode`, `image` и `alt`; контейнер, сетка, порядок секций и aspect ratio остаются прежними.

## 6. Content model

Content не вшивается в layout-компоненты. Данные должны жить в локальной collection или эквиваленте будущего стека.

```ts
type ImageAsset = {
  kind: 'placeholder' | 'image'
  src?: string
  alt: string
  width?: number
  height?: number
  aspectRatio: string
}

type Article = {
  slug: string
  category: 'learn' | 'how-to' | 'announcements'
  title: string
  excerpt: string
  publishedAt: string
  author?: string
  cover: ImageAsset
  content: Block[] | MDX
  tags?: string[]
  relatedSlugs?: string[]
  featured?: boolean
}
```

Обязательные поля карточки: `title`, `excerpt`, `cover`, `href`. Карточка не знает своей категории и не содержит вложенных ссылок. ArticleLayout строит TOC из фактических `h2` со стабильными id, а `/search` экранирует query в заголовке.

## 9. Последовательность следующих этапов

1. **Этап 2 — только после отдельной команды:** принять реальный стек, создать/расширить tokens, site shell, доступную навигацию, базовые компоненты и `ProductDeviceMockup`; проверить lint/typecheck/build, если они появятся в проекте.
2. **Этап 3:** собрать `/` в семи секциях, используя только серые mockups и copy выше.
3. **Этап 4:** добавить data-driven контентные маршруты, статьи, поиск, pricing/FAQ/about/support без неподтверждённых фактов.
4. **Этап 5:** визуальная, responsive, accessibility и performance QA; создать отдельный QA report.

До получения исходного веб-проекта никаких файлов реализации, роутов, зависимостей, публикаций или внешних форм не создаётся.

## 10. Риски, допущения и вопросы

### Допущения, сделанные в этом плане

- Основная аудитория работает с клиентами и встречами; это следует из подтверждённых сущностей продукта, а не из отраслевых обещаний.
- Главная будет на русском языке, потому что текущие проектные материалы и UI русифицированы. Локализация на другой язык **требует подтверждения**.
- Первые шесть feature-карточек используют подтверждённые iPhone-сценарии вместо неподтверждённых воронки, сегментов и аналитики.
- У сайта пока нет разрешённого сервиса для email-формы или demo-request; CTA не отправляют данные.
- Реальные product shots заменят placeholders после утверждения главной, без изменения layout.

### Блокирует начало Этапа 2

1. Где находится целевой веб-репозиторий и какой стек/package manager в нём уже принят? В текущей папке нет кода, поэтому создавать новый стек по догадке небезопасно. Если сайта ещё нет, нужно явное разрешение и выбранный стек для его инициализации.
2. Нужен прозрачный исходник логотипа (предпочтительно SVG) или явное разрешение на подготовку production-версии из предоставленного raster reference.

### Не блокирует shell, но требует подтверждения до соответствующих страниц/CTA

- утверждённый primary CTA: демо, регистрация, звонок или иной путь;
- реальные контактные каналы и часы поддержки;
- тарифы, условия trial и цены;
- точная продуктовая политика о данных, доступах и безопасности;
- отзывы, team portraits, темы/авторы/даты статей;
- допустимые к публикации Figma frame URL и скриншоты, особенно широкий экран для showcase;
- точный брендовый цвет, wordmark и правила использования логотипа.
